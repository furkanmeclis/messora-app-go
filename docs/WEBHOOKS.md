# Outgoing webhooks

Messora can push events to your systems: a new customer message, a closed
conversation, a finished campaign, an opt-out. You register an HTTPS URL,
choose the events, and Messora sends a signed `POST` for each event.

Endpoints are managed in the panel (**Settings → Webhooks**, permission
`webhooks.manage`) or through the API (`/api/v1/webhook-endpoints`, same
scope for API keys). See [`api/openapi.yaml`](../api/openapi.yaml) for the
exact operations.

Every workspace has its **own** endpoints, signing secrets and delivery log:
they live in tenant tables under row-level security, their tasks carry the
workspace in the queue header, and their Redis budgets sit under the
workspace's key prefix. The API calls below go to the workspace's own address
(`https://<workspace>.messora.tech/api/v1`, see [API.md](API.md)). How many
endpoints a workspace may register and how many deliveries per minute it gets
come from its plan ([ENTITLEMENTS.md](ENTITLEMENTS.md)); a plan without the
`webhooks` feature answers `403 FEATURE_NOT_IN_PLAN`.

## Registering an endpoint

```http
POST /api/v1/webhook-endpoints
Authorization: Bearer msk_live_…
Content-Type: application/json

{"url": "https://crm.example.com/hooks/messora",
 "description": "CRM sync",
 "event_types": ["message.received", "conversation.closed"]}
```

The response contains the endpoint and its **signing secret** (`whsec_…`).
The secret is generated by Messora, stored encrypted and shown only in this
response and after `POST /webhook-endpoints/{id}/rotate-secret`.

**Rotation with overlap.** `POST /webhook-endpoints/{id}/rotate-secret` with
`{"grace_hours": 24}` (the default; 0–168) issues a new secret and keeps the
previous one valid for the overlap: every delivery in that time carries two
signatures, `t=…,v1=<new>,v1=<old>`, so the receiver can switch to the new
secret whenever it likes without rejecting a single event.
`previous_secret_expires_at` on the endpoint says until when. With
`{"grace_hours": 0}` the old secret stops at once, also for retries of
earlier events. Only one previous secret is kept: a second rotation during
the overlap replaces it.

URL rules (SSRF protection, see [SECURITY.md](SECURITY.md)):

- `https://` only. Plain `http://` is accepted only when Messora runs with
  `APP_ENV=development`.
- The host must resolve to public addresses only. Loopback, private
  (10/8, 172.16/12, 192.168/16, fc00::/7), link-local (including
  169.254.169.254), CGNAT (100.64/10), multicast and reserved ranges are
  refused, also in IPv4-mapped or NAT64 form, and also when only one of the
  host's addresses is private. Numeric shortcuts such as `2130706433` or
  `0177.0.0.1` are refused.
- The check runs when the endpoint is saved **and again on every request**
  (at connection time): the client resolves the name itself, checks every
  address and dials the checked address, and the socket hook checks it once
  more, so a DNS change (rebinding) cannot redirect deliveries into the
  server's network or to the cloud metadata service (169.254.169.254,
  `fd00:ec2::254`, 100.100.100.200, also as IPv4-mapped, NAT64, 6to4 or
  Teredo IPv6).
- No credentials in the URL (`https://user:pass@…`) and no fragment.
  Redirects are not followed: register the final URL.

`POST /webhook-endpoints/{id}/test` sends a `webhook.test` event to one
endpoint (also while it is disabled), which is the quickest way to check a
receiver.

## Request format

```http
POST /hooks/messora HTTP/1.1
Content-Type: application/json
User-Agent: Messora-Webhooks/1
Messora-Event-Id: 01a207bd-bfc2-729b-b21e-020333b3cae2
Messora-Event-Type: message.received
Messora-Delivery-Id: 01a207bd-bfc7-77ba-944c-d318d6e8ef09
Messora-Delivery-Attempt: 1
Messora-Signature: t=1795426205,v1=e3d1cf83…

{"id":"01a207bd-bfc2-729b-b21e-020333b3cae2","type":"message.received","version":1,
 "created_at":"2026-11-23T09:30:05.123Z","data":{…}}
```

Every body is an envelope:

| Field | Meaning |
|---|---|
| `id` | Event ID (UUIDv7). The same on every retry and redelivery: **use it to drop duplicates.** Also sent as `Messora-Event-Id`. |
| `type` | One of the event types below. |
| `version` | Payload version, currently `1`. New fields may appear without a version change; a field changing meaning bumps it. |
| `created_at` | When the event happened (UTC). |
| `data` | Event-specific payload. |

Delivery is **at least once** and **not ordered**: an event may arrive more
than once (dedupe on `id`), and a retried event may arrive after a newer one
(compare `data` timestamps if order matters).

## Verifying the signature

`Messora-Signature` is `t=<unix seconds>,v1=<hex>`, where `<hex>` is
HMAC-SHA256 with the endpoint secret over the string `"<t>.<raw body>"`.
Verify against the **raw** request body, compare in constant time and reject
timestamps more than five minutes from your clock (the replay window).
Accept the request when **any** `v1` value matches: during a secret
rotation's overlap there are two. A replayed request older than the window
fails even with a valid signature; a fresh delivery attempt always carries a
fresh timestamp.

Node.js:

```js
import crypto from 'node:crypto';

function verify(secret, header, rawBody, toleranceSec = 300) {
  const parts = Object.fromEntries(header.split(',').map((p) => p.split('=')));
  const t = Number(parts.t);
  if (!t || Math.abs(Date.now() / 1000 - t) > toleranceSec) return false;
  const want = crypto.createHmac('sha256', secret).update(`${t}.${rawBody}`).digest();
  const got = Buffer.from(parts.v1 ?? '', 'hex');
  return got.length === want.length && crypto.timingSafeEqual(got, want);
}
```

Python:

```python
import hashlib, hmac, time

def verify(secret: str, header: str, raw_body: bytes, tolerance: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    t = int(parts.get("t", "0"))
    if abs(time.time() - t) > tolerance:
        return False
    want = hmac.new(secret.encode(), f"{t}.".encode() + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(want, parts.get("v1", ""))
```

Go receivers can use `webhooks.Verify` from
`internal/modules/webhooks/signature.go` as a reference.

## Responses, retries and the delivery log

Answer quickly (within 10 seconds) with a `2xx`; do slow work after
answering. Messora reads at most 16 KiB of your answer and keeps the first
KiB in the delivery log.

| Your answer | What Messora does |
|---|---|
| `2xx` | Succeeded. |
| `410 Gone` | Failed, and the **endpoint is switched off** (`disabled_reason` is set). Re-enable it in the panel or with `PATCH {"active": true}`. |
| `408`, `429`, `5xx`, timeout, connection error | Retried. `Retry-After` (seconds or HTTP date, capped at 12 h) is honoured on `429` and `503`. |
| Any other `4xx`, any `3xx` | Failed without retries: fix the receiver, then redeliver. |
| Destination refused (private address) | Failed without retries. |

Retries back off: 1 min, 5 min, 15 min, 30 min, 1 h, 2 h, 4 h, 6 h, 10 h
(±10% jitter), so a delivery is tried **10 times over about 24 hours**
before it fails for good. The retry plan is stored in PostgreSQL and
survives restarts.

### Health and automatic switch-off

Every attempt counts towards the endpoint's health: `failure_streak` is the
number of attempts that failed in a row (a success resets it),
`failing_since` when the run began, `last_success_at` / `last_failure_at`
the latest of each. When **20 attempts in a row** have failed and the run is
at least **24 hours** old, Messora switches the endpoint off
(`active: false`, `disabled_reason`, `disabled_at`), records
`webhook.disable` in the audit log and e-mails the workspace's owners and
admins (branded `webhook_disabled` e-mail, Turkish or English, with a link
to the webhook settings). Both conditions matter: a busy endpoint's short
outage (many failures within minutes) is ridden out by the retries, a dead
one stops costing deliveries after a day. A `410 Gone` switches the endpoint
off at once (same e-mail).

A switched-off endpoint gets no new events and its scheduled retries fail
with `endpoint is disabled`; test events still reach it. **Re-enable** it in
the panel (the status column has a button) or with `PATCH {"active": true}`:
that clears `disabled_reason` and `disabled_at` and starts the failure count
over. Redeliver what was missed from the delivery log.

### Delivery budgets (fair share)

- Deliveries are queue tasks of the workspace (`messora-tenant` header), so
  the worker's per-tenant share (docs/ARCHITECTURE.md §10.1) applies: one
  workspace's backlog cannot take every worker slot.
- **Per endpoint:** a worker process sends at most 4 deliveries to one
  endpoint at a time, and only **one** while the endpoint is failing (3 or
  more failures in a row). A slow or broken receiver therefore holds at most
  that many slots; the rest of the workspace's deliveries, and every other
  workspace's, keep flowing. The cap is per process (in memory, nothing
  leaks when a worker dies).
- **Per workspace:** the plan's `webhook_deliveries_per_minute` (default
  1200) is a budget shared by every worker through Redis.
- Over a budget the task is put back for a moment (no attempt is counted
  and no retry budget is spent).

`GET /webhook-endpoints/{id}/deliveries` lists deliveries with status
(`pending`, `delivering`, `retrying`, `succeeded`, `failed`), attempts, last
HTTP status, duration, error and response excerpt.
`POST /webhook-deliveries/{id}/redeliver` sends a delivery again with a fresh
attempt budget (same event ID, new signature). Events and their delivery log
are kept for 30 days.

Disabling an endpoint (or deleting it) stops new deliveries; deliveries that
are already scheduled fail with `endpoint is disabled`.

## Events

Subscribe with `event_types`; `GET /api/v1/webhook-event-types` returns the
catalogue. Events are recorded in the same database transaction as the change
they describe: an event is never sent for a change that was rolled back, and
a committed change always produces its event.

> **Customer data.** Payloads contain phone numbers and names, and
> `message.received` contains the message text, because integrations need
> them. Treat webhook bodies like the rest of your customer data. Payloads
> never contain secrets, tokens or media files.

### `message.received`

A customer sent a message.

```json
{
  "message_id": "01a2…", "wamid": "wamid.HBgM…", "conversation_id": "01a2…",
  "phone_number_id": "01a2…", "direction": "inbound", "message_type": "text",
  "status": "received",
  "contact": {"id": "01a2…", "phone": "+905551112233", "name": "Ali"},
  "text": "Where is my order?", "reply_to_wamid": null,
  "occurred_at": "2026-11-23T09:30:04Z"
}
```

`text` is the readable part of the message: the text body, the caption of a
media message, the title of a tapped button or list item, a reaction emoji
or a location's name and address (empty when there is none). `message_type` is WhatsApp's type (`text`, `image`,
`button`, `interactive`, …). Media files are not included; read them through
the API.

### `message.status`

A message's delivery state changed: `sent` (accepted by Meta), `delivered`,
`read`, `failed`, or `unknown` (Meta's answer was lost; Messora waits for its
status update and never re-sends on its own). Same fields as `message.received` without `text`, plus
`campaign_id` for campaign messages and `error` (`{"code", "title"}`) for
failures. Only actual changes are emitted; out-of-order status updates from
Meta that do not advance the state are not.

### `conversation.assigned`, `conversation.closed`, `conversation.reopened`

```json
{
  "conversation_id": "01a2…", "phone_number_id": "01a2…",
  "contact": {"id": "01a2…", "phone": "+905551112233", "name": "Ali"},
  "status": "open", "assignee_id": "01a2…",
  "actor": {"type": "user", "id": "01a2…"}
}
```

`conversation.assigned` is also sent when a conversation is unassigned
(`assignee_id` is `null`). `actor.type` is `user`, `api_key` or `system`; a
closed conversation reopened by a new customer message has the `system`
actor.

### `campaign.completed`, `campaign.failed`, `campaign.cancelled`

```json
{
  "campaign_id": "01a2…", "name": "November launch", "status": "completed",
  "total_recipients": 1200,
  "counts": {"recipients_queued": 1180, "recipients_skipped": 20, "sent": 300, "delivered": 850, "read": 20, "failed": 10},
  "last_error": null, "started_at": "…", "finished_at": "…"
}
```

`counts` are the counts at the moment the campaign finished; statuses keep
arriving afterwards as `message.status`.

### `contact.created`, `contact.updated`, `contact.opted_out`, `contact.opted_in`

```json
{
  "contact_id": "01a2…", "phone": "+905551112233", "name": "Zeynep",
  "email": null, "opted_out": true, "opted_out_at": "…", "source": "api",
  "updated_at": "…"
}
```

`contact.created` and `contact.updated` are sent for changes made in the
panel or through the API. Contacts created by an incoming message are
announced by `message.received`; CSV/Excel imports do not emit per-contact
events. `contact.opted_out` and `contact.opted_in` are sent only when the
consent state actually changes.

### `webhook.test`

Sent by "send test event"; cannot be subscribed to.

```json
{"endpoint_id": "01a2…", "message": "This is a test event from Messora."}
```

## For operators

- Delivery runs in the worker (`webhook:fanout` and `webhook:deliver` on the
  `default` queue); the API never calls receivers.
- The SSRF guard lives in `internal/platform/safehttp`. Its only way to reach
  every private address, `Options.AllowPrivate`, panics outside Go test
  binaries, so no setting can turn the protection off.
  `WEBHOOK_ALLOWED_CIDRS` (comma-separated, e.g. `10.20.0.0/16`) is an
  explicit allowlist of internal receivers: networks wider than /8 (IPv4) or
  /32 (IPv6), and networks containing a metadata service or loopback, are
  refused at start-up. The E2E stack uses it for a receiver on the test
  host; production normally leaves it empty.
- Up to 50 endpoints can be registered on the default plan (the plan
  decides, [ENTITLEMENTS.md](ENTITLEMENTS.md)). Endpoint changes, secret
  rotations, redeliveries and automatic disabling are recorded in the audit
  log (secrets never are).
- The signature header is `Messora-Signature` (no `X-` prefix, RFC 6648);
  it has been the contract since the first release and stays.
