# WhatsApp Cloud API integration

Messora talks only to Meta's official WhatsApp Cloud API (Graph API, default
version `v26.0`, configurable with `META_GRAPH_API_VERSION`).

## Connecting an account

1. In Meta Business Suite create a **system user**, give it the
   `whatsapp_business_messaging` and `whatsapp_business_management`
   permissions on your WhatsApp Business Account (WABA), and generate a
   permanent access token.
2. In Messora open **Channels** (or call `POST /api/v1/channels/accounts`) and
   enter a name, the WABA ID, the access token and, ideally, the app secret.
   The token is checked against Meta before anything is stored; phone numbers
   and templates are imported. Tokens and app secrets are encrypted with
   `APP_ENCRYPTION_KEY` and never returned by the API.
3. Alternatively set `META_WABA_ID`, `META_ACCESS_TOKEN` (and `META_APP_ID`,
   `META_APP_SECRET`) in `.env`; the account is connected on first start,
   and a changed `META_ACCESS_TOKEN` replaces the stored token on restart.

### Keeping the connection alive

Tokens copied from the App Dashboard ("temporary access token") or Graph
Explorer expire within hours or a day; the account then stops sending. Use a
**System User** token with *Token expiration: Never* (Business Settings →
Users → System users → Generate new token). The panel walks through it.

Messora asks Meta about every token (`debug_token`) when it is connected or
replaced, and again every six hours:

- invalid tokens, missing `whatsapp_business_messaging` /
  `whatsapp_business_management` permissions and tokens without access to
  the WABA are refused with the reason;
- the token's type and expiry are shown under Channels; an expiring token is
  flagged, and owners and admins are e-mailed a week before it stops working
  (and when Meta refuses it), at most once a day;
- with the App ID and app secret, a short-lived user token is exchanged for a
  long-lived (about 60 days) one automatically;
- replacing the token of a flagged account brings it back into service at
  once; **Check connection** re-validates on demand.

## Webhooks

`GET /api/v1/channels/webhook` (panel: Channels → Webhook) shows the values for
the Meta App dashboard:

| Field | Value |
|---|---|
| Callback URL | `<PUBLIC_APP_URL>/webhooks/whatsapp` (must be public HTTPS) |
| Verify token | `META_VERIFY_TOKEN` (generated by `messora-init`) |
| Fields | `messages`, `message_template_status_update`, `message_template_quality_update`, `phone_number_quality_update`, `account_update`, `business_capability_update`, `user_preferences` |

Subscribe the app to **every** field in the list (Meta App dashboard →
WhatsApp → Configuration → Webhook fields → *Subscribe*). Fields that are not
subscribed are simply never sent: Messora cannot detect it. What each field
is used for:

| Field | Used for |
|---|---|
| `messages` | inbound messages and delivery statuses, including the `pricing` object (see [Cost and account signals](#cost-and-account-signals)) |
| `message_template_status_update` | template review results, pausing and disabling |
| `message_template_quality_update` | template quality score (`GREEN`/`YELLOW`/`RED`/`UNKNOWN`) on the template |
| `phone_number_quality_update` | portfolio messaging limit and throughput upgrades; triggers a re-read of the number's quality rating |
| `business_capability_update` | portfolio messaging limit changes |
| `account_update` | restrictions, violations, bans, offboarding … — stored as account events |
| `user_preferences` | a customer stopped or resumed marketing messages in WhatsApp |

Every POST must carry a valid `X-Hub-Signature-256` made with the app secret
(`META_APP_SECRET` or the account's app secret). **Without an app secret all
webhooks are rejected** — Messora never accepts unsigned events.

Processing:

- The raw body is stored (`webhook_events`) before `200 OK` is returned, and a
  worker task processes it. Meta retries for up to 7 days; identical bodies are
  stored once, and inbound messages are unique by WhatsApp message ID, so
  retries never create duplicates.
- Delivery statuses are applied **monotonically** (sent → delivered → read).
  Meta does not guarantee order: a late `delivered` after `read` only fills in
  `delivered_at`; `failed` is accepted only before delivery.
- A status for a message Messora has not yet matched (the send response may
  still be in flight) is retried for 15 minutes before it is dropped.

## Sending and delivery guarantees

`POST /api/v1/messages` stores the message and schedules sending in the same
transaction, then returns `202` with status `pending`. Use an
`Idempotency-Key` header to retry the request itself safely.

Meta's send API has no idempotency key, so Messora is careful about what it
retries:

| Outcome | Examples | What happens |
|---|---|---|
| Accepted | Meta returned a message ID | `sent`; webhooks advance it |
| Definitely not sent | connection refused, DNS failure, `130429` throughput, `131056` pair rate, `131000`/`131016`/`133004` transient, HTTP 429 | back to `pending`, retried with backoff (up to 8 attempts) |
| Rejected | `131047` outside 24 h window, `132xxx` template errors | `failed` with Meta's code (`failure_class` `rejected_by_meta`) |
| Rejected for this customer | `131050` stopped marketing in WhatsApp, `131026` undeliverable | `failed`; the contact is flagged (stopped marketing / undeliverable) and further sends of that kind are refused before Meta — see [CONSENT.md](CONSENT.md) |
| Ecosystem limit | `131049` marketing withheld for this user | `deferred`, retried no earlier than 24 h later without holding a campaign window slot; `failed` (`ecosystem_limit`) after three attempts |
| Blocked by consent | the contact opted out after the message was queued | `skipped` right before sending (`failure_class` `blocked_by_consent`, reason in `error_code`) |
| Account problem | `0`/`190` token, `10`/`200-299` permission, `368`/`131031` restriction | `failed`; the account is flagged `error` with a readable reason (expired, invalidated, missing permission), owners and admins are e-mailed, and further sends fail fast until the connection check passes or the token is replaced |
| **Unknown** | timeout after the request was written, connection reset, gateway 5xx without Meta's error body, worker crash mid-send | `unknown`; **never re-sent automatically** |

Unknown messages are reconciled by the status webhook: Messora puts its own
message ID in `biz_opaque_callback_data`, which Meta echoes in status
updates, so a message whose response was lost still becomes `sent`,
`delivered` or `read`.

Outside the 24-hour customer service window only approved templates are
accepted (`422 OUTSIDE_SERVICE_WINDOW`); the window opens with the
customer's last inbound message to the sending number (reactions and system
notices do not open it).

## Cost and account signals

### Message cost

Meta charges per delivered message (per-message pricing). The status webhook
carries a `pricing` object — on the `sent` **or** the `delivered` status,
never both — with `type` (`regular` = charged; `free_customer_service`,
`free_entry_point`, … = free), `category` (`marketing`, `utility`,
`authentication`, `authentication-international`, `service`, …),
`pricing_model` and the deprecated `billable`. **It contains no amount.**

Messora stores these on the message (`pricing_type`, `pricing_category`,
`pricing_model`, `billable`) together with the recipient's country
(`recipient_country`, derived from the number's calling code), and prices it:

- a free type costs `0` (`cost_source = free`);
- a `regular` message gets the price of the imported **rate card** for the
  recipient's market and the category, in the account's currency, valid on
  the day the message was sent (`cost_source = rate_card`). For tiered
  categories (utility, authentication) the tier is chosen by how many billable
  messages of the same category went to the same market earlier in the
  calendar month;
- without a matching rate the cost stays empty — Messora never guesses.

A later status without `pricing` never clears stored values. The message API
returns `pricing_category`, `pricing_type`, `cost_amount` (decimal string)
and `cost_currency`.

### Rate card

Meta publishes no pricing API; prices are published as a rate card per
currency (<https://developers.facebook.com/docs/whatsapp/pricing>) and change
at the start of quarters. Messora ships **no prices**. Convert Meta's card
into the CSV below and import it under **Settings → Meta rate card** (or
`POST /api/v1/settings/meta-rates/import`, multipart field `file`, permission
`settings.update`). `GET /api/v1/settings/meta-rates` lists what is stored.

```csv
market,countries,category,price,currency,effective_from,tier_lower,tier_upper,source
Turkey,TR,marketing,0.0000,USD,2026-10-01,,,Meta rate card 2026-10
Turkey,,utility,0.0000,USD,2026-10-01,1,100000,Meta rate card 2026-10
Turkey,,utility,0.0000,USD,2026-10-01,100001,,Meta rate card 2026-10
Rest of Western Europe,AT;BE;CH;…,marketing,0.0000,USD,2026-10-01,,,Meta rate card 2026-10
Other,,marketing,0.0000,USD,2026-10-01,,,Meta rate card 2026-10
```

| Column | Meaning |
|---|---|
| `market` | Meta's market name: a country ("Turkey") or a group ("Rest of Western Europe"). Countries without their own row use the market `Other`. |
| `countries` | ISO 3166 alpha-2 codes of the market, separated by spaces, `;` or `\|`. Needed on one row of the market only; a country belongs to one market. |
| `category` | `marketing`, `utility`, `authentication`, `authentication-international` or `service` |
| `price` | price per message, dot decimal, at most 6 decimals (`0.0436`) |
| `currency` | ISO 4217 code; must be your WhatsApp account's currency (shown under Channels; read from Meta) |
| `effective_from` | first day the price applies (`YYYY-MM-DD`). A price is valid until the next `effective_from` of the same currency, market and category, so importing a new quarter keeps the history. |
| `tier_lower`, `tier_upper` | optional volume tier: the message's number within the calendar month, inclusive (`1`–`100000`, then `100001`–empty). Leave both empty for untiered prices. |
| `source` | optional note (e.g. which card the row came from) |

The delimiter may be `,` or `;` (as Excel saves it in many locales). The
whole file is rejected, with every problem listed, when any row is invalid;
re-importing the same file changes nothing.

### Meta's own cost (reconciliation)

Once a day (`meta_cost_reconcile`) Messora asks Meta's `pricing_analytics`
for the last three days (daily granularity, broken down by phone number,
country, pricing category and pricing type; metrics `COST` and `VOLUME`)
and stores the figures in `meta_cost_daily`. Meta calls these costs
approximate; they are in the account's currency. Accounts that use a
solution partner's credit line get volumes without cost — the cost column
stays empty.

### Number and account signals

Every hour (`whatsapp_signal_sync`), after an account is connected and on
**Sync**, Messora reads per number the `quality_rating`, the messaging
limit (`whatsapp_business_manager_messaging_limit`, which is the business
portfolio's) and the `throughput` level (`STANDARD` = 80, `HIGH` = 1,000
messages per second), and the account's `currency`. The send throttle uses
each number's throughput as its ceiling (80 while unknown) and still halves
the rate on Meta's throughput error.

Webhooks keep these current between syncs: `phone_number_quality_update`
(limit changes, `THROUGHPUT_UPGRADE`; it also triggers a sync because it
does not carry the quality rating), `business_capability_update` (limit),
`message_template_quality_update` (the template's `quality_score`).
These and `account_update` alerts (restrictions, violations, bans,
offboarding …) are kept in `whatsapp_account_events`.

`user_preferences` (a customer chose *Stop* or *Resume* for the business's
marketing messages in WhatsApp) is stored append-only in
`meta_user_preferences` and raised as the internal event
`meta.user_preference`, which sets the contact's "stopped marketing in
WhatsApp" flag (Resume clears it; see [CONSENT.md](CONSENT.md)). Meta then rejects marketing templates to that
customer with error `131050`.

## Inbox

Messages are grouped into **conversations**, one per customer and business
number. A conversation is never stored separately from its messages: every
inbound or outbound message write updates it in the same transaction
(`internal/modules/messaging/conversation.go`).

- **Window.** `last_inbound_at` is the last window-opening customer message;
  `window_open` / `window_expires_at` (= `last_inbound_at` + 24 h) tell the
  panel whether a free-form reply is possible. The same value is what
  `messaging.Queue` checks for every non-template message, from the inbox
  and from `POST /messages` alike. Consent is checked for every message
  (`422 CONTACT_OPTED_OUT`, `MARKETING_STOPPED`, `CONTACT_UNDELIVERABLE`,
  `OPT_OUT_REQUESTED`, `CONSENT_UNKNOWN`); the rules per category are in
  [CONSENT.md](CONSENT.md).
- **Visibility.** `conversations.read_all` (owner, admin, manager) sees
  everything. With only `conversations.read` (agent) a user sees
  conversations assigned to them or to nobody, on every endpoint: list,
  detail, history, media, events, mark read, reply and the
  `conversation:<id>` realtime channel. Anything else answers `404`, the same
  as a conversation that does not exist. API keys follow the same rule (a key
  is never an assignee, so `conversations.read` gives the unassigned ones).
- **Assignment and status** need `conversations.assign`. Assignees must be
  active users who can read conversations. Closing is a team decision; the
  next customer message reopens the conversation automatically (recorded as
  a `reopened` event without an actor). Outbound messages never reopen.
  Every change is kept in the conversation's history and in the audit log.
- **Unread** counts customer messages for the whole team and is reset by
  `POST /conversations/{id}/read` (the panel does it when a conversation is
  opened).
- **Media** of inbound messages is downloaded by the worker and served by
  `GET /conversations/{id}/media/{mediaId}` after the visibility check, with a
  parsed Content-Type, `inline` disposition only for common image, video and
  audio types (everything else, including SVG and HTML, is an attachment),
  `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`.
  The panel loads files through the `/bff/media/...` route, never directly.
- **Realtime.** `conversation.updated` (IDs, status, assignee, unread count)
  goes to `inbox:all` and `conversation:<id>`; message events carry
  `conversation_id`. Events on `inbox:all` contain identifiers only; the
  panel re-reads the data through the API with the user's permissions.

## Media

Inbound media (image, video, audio, document, sticker) is downloaded by the
worker into the `messora-media` volume (`MEDIA_DIR`) before Meta's 7-day
expiry, with size (100 MB) and checksum checks. Outbound media is sent by Meta
media ID or by HTTPS link.

## Testing without Meta

- `internal/modules/whatsapp/whatsapptest` is a programmable Graph API mock:
  it scripts Meta error codes, slow answers, dropped connections and gateway
  errors, and builds signed webhook payloads (statuses with a `pricing`
  object, `user_preferences`, quality, capability, account and template
  quality updates). It also answers `GET /{waba}?fields=currency` and a
  scriptable `pricing_analytics`. The integration tests in
  `internal/app/whatsapp_integration_test.go` and
  `internal/app/metacost_integration_test.go` drive the whole flow with it.
- `META_DRY_RUN=true` refuses every request to Meta's hosts; it is forced on
  when `APP_ENV=test`, so tests can never message real customers.
- `META_GRAPH_BASE_URL` points the client at another host (the mock).

## Manual smoke test with a real test number

Run only with a Meta **test** number and recipients who agreed to receive test
messages.

1. Create a Meta app with the WhatsApp product; note the test number's phone
   number ID, the WABA ID, a System User token and the app secret (a
   temporary token works for a quick test but expires within a day).
2. Expose Messora over public HTTPS (`SITE_ADDRESS=your.domain`).
3. Connect the account in the panel; confirm the number and templates appear.
4. In the Meta App dashboard subscribe the webhook with the values from
   Channels → Webhook; Meta's verification request must succeed.
5. From the recipient's phone send "hi" to the test number; the message appears
   in `messages` with status `received`.
6. Send a text reply via `POST /api/v1/messages`; it becomes `sent`, then
   `delivered` and `read` as the recipient opens it.
7. Send the `hello_world` template to a recipient who has not written in 24 h.
8. Send an image from the phone; the file appears under the media volume.
9. Rotate the token in the panel; sending keeps working.

## Templates with variables and media

Campaigns, inbox replies and automation steps fill a template the same way
(`template_params`, or `template.params` on an inbox reply):

| Field | Fills |
|---|---|
| `header` / `body` | variables: a list for `{{1}}` templates, an object for named ones. Values are fixed text or contact placeholders: `{{name}}`, `{{first_name}}`, `{{phone}}`, `{{email}}`, `{{var1}}`…`{{var5}}`, `{{attr:<key>}}` |
| `buttons` | the dynamic end of URL buttons, by button position (`["", "summer-sale"]` fills button 2) |
| `fallback` | a value for a placeholder that is empty for a contact; without it the contact is skipped |
| `header_media` | the image, video or document of a media header: an uploaded media `id` (kept 30 days by Meta) or a public `https` `link` |
| `location` | a location header: `latitude`, `longitude` (decimal degrees, sent as strings like Meta's examples), optional `name` and `address` (placeholders allowed) |
| `coupon_code` | the code of the copy code button (15 characters in limited-time offers) |
| `expiration_time_ms` | when a limited-time offer ends (Unix milliseconds); WhatsApp counts down to it |
| `cards` | carousel cards in order: each `header_media`, `body` and `buttons` (URL suffix, or a quick reply's payload, by button position) |
| `otp_code` | the code of an authentication template; Meta's body and the OTP button both take it |
| `flow` | a Flow button: `flow_token` (Meta's default `unused`) and `flow_action_data` for the first screen |

Before a campaign starts (and before an inbox reply or automation step is
sent) the values are checked against the template: a missing header image,
location, variable, URL button suffix, coupon, offer end or card is reported
instead of failing at Meta for every recipient.

The send payload follows Meta's examples: components in the order header,
body, `limited_time_offer`, buttons by index, `carousel`. Button `index` is
the button's position in the template, so in a limited-time offer with a
copy code button the URL button is index 1 (Meta: "if the template uses a
copy code button, value must be 1"). Messora sends indexes as strings; Meta's
own examples use both (carousel: strings, LTO: numbers).

Creating a media-header template needs an example file for Meta's review:
the panel uploads it with `POST /api/v1/templates/samples` (Meta's Resumable
Upload API, which needs the account's App ID).

## Template components

`POST /api/v1/templates` checks the components against the limits Meta
documents before anything is submitted
(`internal/modules/channels/components.go`); a violation is a
`VALIDATION_ERROR` whose `field` names the component, e.g.
`components.2.buttons.1.text`. The panel's builder (`/templates/new`)
checks the same limits as you type.

| Component | Rules |
|---|---|
| Header | `TEXT` (60 characters, one variable with a sample), `IMAGE` / `VIDEO` / `DOCUMENT` (sample `header_handle` from `POST /templates/samples`), `LOCATION` (utility and marketing only; the place is given when sending). `GIF` is refused (Marketing Messages API only). |
| Body | required; 1024 characters (600 in limited-time offers); `{{1}}, {{2}}…` without gaps or named `{{first_name}}` matching `parameter_format`; a sample for every variable |
| Footer | 60 characters, no variables; not in limited-time offers or carousels |
| Buttons | at most 10: quick reply ≤ 10 (kept in one block, before or after the others), URL ≤ 2 (one variable, at the end, with a sample), phone number ≤ 1 (20 characters), copy code ≤ 1 (sample ≤ 20), `VOICE_CALL` (label ≤ 20, `ttl_minutes` 1440–43200), `FLOW` (exactly one of `flow_id`, `flow_name`, `flow_json`; `flow_action` `navigate` or `data_exchange`). Labels ≤ 25 characters. |
| Catalog | `MPM`, `SPM`, `CATALOG` buttons are refused: they need a connected product catalog, which Messora does not manage |
| Carousel | marketing only; a body and 2–10 cards and nothing else; every card has an image or video header (all the same), an optional body (≤ 160, on all cards or none) and up to two quick reply / URL / phone buttons in the same order on every card |
| Limited-time offer | marketing only; no footer; header optional, image or video; `limited_time_offer.text` ≤ 16; buttons: an optional copy code (sample ≤ 15) and exactly one URL button. The end is not part of the template: each message carries `expiration_time_ms`. WhatsApp web and desktop show that the offer is not supported. |
| Authentication | Meta writes the body ("<code> is your verification code.") and footer: `BODY` takes only `add_security_recommendation`, `FOOTER` only `code_expiration_minutes` (1–90); exactly one `OTP` button: `COPY_CODE`, `ONE_TAP` or `ZERO_TAP` (the last two need 1–5 `supported_apps` with `package_name` and an 11-character `signature_hash`; zero-tap needs `zero_tap_terms_accepted: true`). Meta stores the OTP button as a URL button, which is how Messora recognises it after a sync. |

Not verified against a live account (taken from Meta's reference pages):
the maximum of one `VOICE_CALL` and one `FLOW` button per template (Meta
names none; Messora allows one each), and whether utility templates may
carry a copy code button.

## Offers

An offer (`/api/v1/offers`, permissions `templates.read` / `templates.manage`;
panel: Templates → Offers) is what a campaign promotes: title, description,
discount, product, start and end, image (`image_url` https and/or
`image_media_id`), offer page, coupon and the template it is meant for.

    draft ─publish (status scheduled)→ scheduled ─starts_at→ active ─ends_at→ expired

The scheduler's `offers:tick` (every minute) moves published offers by the
clock and publishes `offer.updated` on `campaign:all`. Ending an offer by
hand (`PATCH … {"status":"expired"}`) is audited; expired offers are final.

A campaign links one with `offer_id`:

- **Limited-time offer template:** `expiration_time_ms` is always the
  offer's `ends_at`; the copy code button takes the offer's coupon unless
  the campaign set one; an empty image header takes the offer's image.
- **Normal marketing template** (e.g. an image header and body variables):
  the image fills an empty image header, and the placeholders
  `{{offer_title}}`, `{{offer_discount}}`, `{{offer_coupon}}`,
  `{{offer_ends}}` (UTC, `2006-01-02 15:04 UTC`), `{{offer_url}}`,
  `{{offer_product}}` and `{{offer_description}}` can be used in any value.
  Only limited-time offer templates show WhatsApp's countdown.
- Creating or editing a campaign with an ended offer is refused (422);
  starting or resuming one is refused with `409 OFFER_EXPIRED`.
- When the offer ends mid-campaign the dispatcher (or the tick) pauses the
  campaign with the event detail `{"reason": "offer_expired", …}`; the
  remaining recipients wait. A scheduled campaign whose offer ended pauses
  the same way when it starts.
